1. INTRODUCTION
1.1 Purpose
This SRS document provides a complete description of all functions and specifications for the
Content Management System (CMS) designed to manage the entire lifecycle of story/content
development from initial idea submission through production and payment.
1.2 Scope
The system will manage:
• Story idea submission and categorization
• Multi-stage approval workflow
• Meeting scheduling and call report generation
• Evaluator scoring and decision tracking
• Contract negotiation and legal vetting

• Script production phases
• Financial tracking and payment schedules
• Comprehensive stakeholder dashboard with drill-down analytics
1.3 Definitions & Acronyms
• CMS: Content Management System
• POC: Point of Contact
• USP: Unique Selling Proposition
• NIC: National Identity Card
• NTN: National Tax Number
• RLS: Row Level Security
• CRUD: Create, Read, Update, Delete

• Workflow Diagram (attached)

2. OVERALL DESCRIPTION
2.1 Product Perspective
This is a standalone web-based application that will:
• Replace manual/email-based content approval processes
• Provide real-time visibility into the content pipeline
• Automate notifications and workflow routing
• Maintain complete audit trail of all actions
2.2 Product Functions
High-level functions include:
1. Story Idea Management
2. Workflow Orchestration (8 stages)
3. User & Role Management
4. Document Management
5. Notification System
6. Reporting & Analytics
7. Audit Trail & Logging

2.3 User Classes & Characteristics
User Role Responsibilities Technical Skill
Content Creator Submit story ideas Low
Content Manager Create call reports, schedule meetings Medium
Evaluator Score and evaluate ideas Low-Medium
Executive Approve one-liners Low
Legal Team Review contracts, vet agreements Medium
Finance Team Track payments, manage schedules Medium
Writer Update script progress Low
Stakeholder/Admin View all data, generate reports Medium-High
2.4 Operating Environment
• Platform: Web-based (accessible via modern browsers)
• Devices: Desktop, Tablet, Mobile (responsive)
• Browsers: Chrome 90+, Firefox 88+, Safari 14+, Edge 90+
• Internet: Required for all operations
2.5 Design & Implementation Constraints
• Must be deployed within 15 days
• Support 50-100 concurrent users initially
• Must scale to 1,000+ users without architectural changes
• Data must be stored securely with encryption
• Must comply with data protection regulations

3.1.2 Functional Requirements
FR-3.1.1: Story Idea Submission Form
• Input Fields Required:

o Title (text, max 200 characters, required)
o Logged By (text, auto-populated from user profile, required)
o Category/Source (dropdown, required):
▪ External Producer
▪ Writer Pitch
▪ In-house Content
o Writer/Originator Name (text, max 100 characters, required)
o Suggested Writer (text, max 100 characters, optional)
o Synopsis (rich text, max 2000 characters, required)
o Genre (dropdown, required):
▪ Drama
▪ Comedy
▪ Action
▪ Thriller
▪ Romance
▪ Documentary
▪ Reality
▪ Other
o Target Audience (text, max 500 characters, required)
o Attachments (file upload, multiple files allowed):
▪ Supported formats: PDF, DOC, DOCX, PPT, PPTX, JPG, PNG
▪ Max file size: 25MB per file
▪ Max total: 100MB per submission

o Story ID
o Title
o Category
o Current Stage
o Status
o Submission Date
o Last Updated

• List must be filterable by:
o Status
o Category
o Date range
o Current stage
• List must support search by title/ID
FR-3.1.6: Story Idea Detail View
• Must display all story information
• Must show current workflow stage
• Must show workflow history (timeline view)
• Must show all attachments with download links
• Must show all comments/notes from various stages
• Must show who is currently assigned the task
3.1.3 Success Criteria
• User can submit story idea in < 5 minutes
• File upload completes successfully 99% of the time
• Validation errors are clear and actionable
• Notifications sent within 1 minute of submission

3.4 EVALUATOR MEETING & SCORING
3.4.1 Description
Multiple evaluators review the Call Report and score the idea based on predefined criteria.
System aggregates scores and determines approval/rejection.
3.4.2 Functional Requirements
FR-3.4.1: Evaluator Assignment
• System must support multiple evaluators per Call Report (minimum 1, maximum 10)
• Evaluators can be:
o Automatically assigned based on genre/category (future enhancement)
o Manually assigned by Content Manager
• System must track assignment:
o Who assigned the evaluator
o When they were assigned
o Notification sent timestamp
FR-3.4.2: Evaluator Dashboard
• Each evaluator must have a "My Tasks" dashboard showing:
o Pending evaluations (awaiting their input)
o In-progress evaluations (saved but not submitted)
o Completed evaluations
• Each task must show:
o Story title
o Call Report ID
o Writer name
o Due date (if set)
o Priority (if set)
o Days pending
FR-3.4.3: Individual Evaluator Form
• Required Information:
o Evaluator Form ID (auto-generated: EF-YYYY-NNNN)
o Evaluator Name (auto-populated, read-only)

o Call Report ID (auto-linked, read-only)
o Meeting Time (datetime, required if meeting held)
o Writer Name (auto-populated from Call Report, editable)
• Criteria Scores (all required):
o Each criterion scored on scale 1-10 (slider or number input)
o Criteria to include:
▪ Originality (1-10)
▪ Market Potential (1-10)
▪ Execution Feasibility (1-10)
▪ Target Audience Appeal (1-10)
▪ Budget Viability (1-10)
▪ Cultural Relevance (1-10)
▪ Competitive Advantage (1-10)
▪ Production Complexity (1-10) - lower is better
▪ [Additional criteria as defined by organization]
• Additional Fields:
o Total Score (auto-calculated, sum of all criteria)
o Average Score (auto-calculated, average of all criteria)
o Target Writer/Writer's Detail (text area, max 1000 characters)
o Per Episode Price Range (Min-Max):
▪ Minimum Price (number, currency)
▪ Maximum Price (number, currency)
o Notes/Comments (rich text, max 2000 characters, required)
o Strengths (text area, max 1000 characters, optional)
o Weaknesses (text area, max 1000 characters, optional)
o Decision (radio button, required):
▪ Approve - Recommend for One-Liner
▪ Reject - Not Suitable
▪ Need More Information - Request Additional Details
FR-3.4.4: Evaluation Scoring Rules
• All criteria must be scored before submission
• System must validate scores are within 1-10 range
• System must calculate totals automatically
• System must prevent submission if required fields missing
FR-3.4.5: Evaluation Log & Aggregation
• System must create "Evaluation Log" showing:
o All evaluator forms for this Call Report
o Individual evaluator names
o Individual scores per criterion
o Individual total scores
o Individual decisions
o Individual comments

• System must calculate aggregated metrics:
o Average score across all evaluators
o Median score
o Approval rate (% who approved)
o Rejection rate (% who rejected)
o Need info rate (% who need more info)
FR-3.4.6: Evaluation Decision Logic The system must determine overall decision based on:
Primary Rule: Unanimous or Majority
• If ALL evaluators approve → APPROVED → Move to One-Liner
• If ALL evaluators reject → REJECTED → Move to Archive
• If MAJORITY approve (>50%) → APPROVED → Move to One-Liner
• If MAJORITY reject (>50%) → REJECTED → Move to Archive
• If ANY evaluator selects "Need More Information" → PENDING → Request additional
info from writer
• If SPLIT decision (50-50) → PENDING → Escalate to Content Manager for tie-breaker
Secondary Rule: Score Threshold
• If average score >= 7.0 AND majority approve → APPROVED
• If average score < 5.0 → REJECTED (regardless of votes)
• If average score 5.0-6.9 → Use majority vote logic
System Configuration:
• Decision rules must be configurable by admin
• Thresholds must be adjustable (7.0, 5.0, etc.)
• Voting requirements must be configurable (unanimous vs majority)
FR-3.4.7: Evaluation Routing Based on decision:
• If APPROVED:
o System updates workflow status to "One-Liner Approval"
o System notifies Executives
o System creates One-Liner task
o System logs approval decision with all evaluator data
• If REJECTED:
o System updates workflow status to "Archived - Rejected at Evaluation"
o System notifies Story Creator and Content Manager
o System logs rejection with reasons from all evaluators
o Story moves to Archive with full history
• If PENDING:
o System notifies Content Manager
o Content Manager contacts writer for clarification

o Process loops back to evaluators after info received
FR-3.4.8: Evaluation Notifications
• When evaluation completed:
o Notify story creator of outcome
o Notify content manager
o If approved: notify executives
o If rejected: provide summary of feedback
• Include in notification:
o Decision outcome
o Aggregate score
o Number of evaluators
o Timeline to next stage
FR-3.4.9: Evaluation History & Audit
• System must record:
o Each evaluator's submission timestamp
o Time taken to evaluate
o Any edits made to evaluation
o Final decision and reasoning
• All data must be visible in stakeholder dashboard
3.4.3 Success Criteria
• Evaluators can complete evaluation in < 15 minutes
• Scoring is intuitive with clear criteria definitions
• Decision logic is transparent and auditable
• Aggregate data provides clear picture for stakeholders
• No manual intervention needed for routing
3.5 DETAILED ONE-LINER APPROVAL
3.5.1 Description
After evaluation approval, executives review a one-liner summary and decide whether to proceed
to negotiation.
3.5.2 Functional Requirements
FR-3.5.1: One-Liner Document
• System must auto-generate One-Liner document containing:

o Story Title
o One-Liner Summary (max 150 characters, distilled from logline)
o Writer Name
o Suggested Price Range (from evaluator forms)
o Average Evaluation Score
o Number of Evaluators Approved
o Key Strengths (from evaluation feedback)
o Estimated Budget (if available)
o Target Delivery Timeline
o Link to full Call Report
o Link to evaluation details
FR-3.5.2: One-Liner Approval Interface
• Executives must see:
o One-liner document (read-only)
o Quick access to all supporting documents
o Historical context (similar projects, if any)
• Executives must make decision:
o Approve - Proceed to Negotiation
o Reject - Decline project
o Request More Info - Send back for clarification
• Additional fields:
o Decision Notes (text area, required for Reject)
o Budget Approval (checkbox, required for Approve)
o Conditions/Caveats (text area, optional)
o Priority Level (dropdown: High, Medium, Low)
FR-3.5.3: One-Liner for Annexure
• System must prepare document for contract annexure
• One-liner linked to future contract
• All approvals and changes tracked
FR-3.5.4: One-Liner Decision Routing
• If APPROVED:
o System updates status to "Negotiation"
o System notifies Content Manager to begin negotiations
o System creates negotiation task
o System logs approval with executive name and timestamp
• If REJECTED:
o System updates status to "Archived - Rejected at One-Liner"
o System notifies all stakeholders
o System logs rejection reason
o Story archived with full history

• If MORE INFO NEEDED:
o System sends back to Content Manager
o Content Manager can update Call Report or gather more data
o Returns to executive for re-review
FR-3.5.5: One-Liner Access Control
• Only executives can approve/reject
• All other roles can view (if in workflow)
• Stakeholders can view all one-liners
FR-3.5.6: One-Liner Notifications
• Executive receives notification when one-liner ready
• Reminder notifications if pending > 3 days
• All stakeholders notified of decision
3.5.3 Success Criteria
• Executive can make decision in < 5 minutes
• One-liner captures essence clearly
• Decision routing is automatic
• No information is lost in workflow

3.7 LEGAL REVIEW & VETTING
3.7.1 Description
Legal team reviews the negotiated terms, vets the writer/producer, and ensures all compliance
requirements are met before contract signing.
3.7.2 Functional Requirements
FR-3.7.1: Legal Review Form
• Input Information:
o Legal Review ID (auto-generated: LR-YYYY-NNNN)
o Story ID (auto-linked)
o Negotiation ID (auto-linked)
o Assigned Legal Reviewer (dropdown, required)
o Review Start Date (auto-generated)
• Contract Checklist (NIC, NTN, etc.): System must provide checklist for Pakistani legal
requirements: Individual Writer/Producer:
o Valid National Identity Card (NIC/CNIC) - uploaded and verified
o National Tax Number (NTN) - provided and verified with FBR
o Bank Account Details - validated
o Previous Work Portfolio - reviewed
o Professional References - contacted (optional)
Company/Production House:
o Company Registration Certificate - uploaded
o NTN (Company) - verified with FBR
o Sales Tax Registration (if applicable)
o Board Resolution for Contract Authority - uploaded
o Authorized Signatory Details - verified

o Company Bank Account Details
o Financial Statements (Last 2 years) - reviewed
Legal Documents:
o Draft Contract Prepared
o Intellectual Property Terms Clear
o Payment Terms Legally Sound
o Termination Clauses Included
o Dispute Resolution Mechanism Defined
o Confidentiality Agreement Signed
o Non-Compete Clause (if applicable)
Compliance:
o Anti-Money Laundering (AML) Check Completed
o Sanctions List Check (OFAC, UN, etc.)
o Background Verification (if required)
o Copyright Clearance (if adapted work)
o Prior Claims Check (no existing disputes)
FR-3.7.2: Document Upload & Verification
• For each checklist item:
o Legal team must be able to upload supporting document
o Mark as Verified/Not Verified/Pending
o Add notes/comments per item
o Set priority (Critical, Important, Nice-to-have)
• System must enforce:
o All "Critical" items must be verified before approval
o All documents stored securely
o Access restricted to Legal and Finance teams
FR-3.7.3: Legal Review Decision
• Legal team makes one of following decisions: APPROVE:
o All critical requirements met
o All documents verified
o Legal team comfortable proceeding

o Fields required:
▪ Final Legal Notes (text area)
▪ Risk Assessment (dropdown: Low, Medium, High)
▪ Special Conditions (text area, optional)
▪ Approved By (auto-populated, legal team member)
▪ Approval Date (auto-generated)
REJECT:
o Critical requirements not met
o Legal concerns cannot be resolved
o Fields required:
▪ Rejection Reason (text area, required, min 100 characters)
▪ Missing Requirements (checklist of what's missing)
▪ Recommendations (text area)
▪ Rejected By (auto-populated)
▪ Rejection Date (auto-generated)
REFUSE (CAN REFUSE IF REQUIREMENTS NOT MET):
o Similar to reject but specifically for missing documents
o Writer/Producer given deadline to provide missing items
o Fields required:
▪ List of Missing Items (auto-populated from checklist)
▪ Deadline to Provide (date picker, required)
▪ Instructions to Writer (text area)
▪ Routing: Returns to Content Manager to collect items
REQUEST MODIFICATIONS:
o Terms need adjustment for legal compliance
o Fields required:
▪ Modifications Required (text area, detailed)
▪ Legal Concerns (text area)
▪ Suggested Changes (text area)
▪ Routing: Returns to Negotiation stage
FR-3.7.4: Legal Review Routing
• If APPROVED:
o System updates status to "Contract Signing"
o System generates contract from template + negotiated terms
o System notifies Finance team to prepare payment schedule
o System notifies relevant parties for signing
o System creates contract signing task
• If REJECTED:

o System updates status to "Archived - Legal Rejection"
o System notifies all stakeholders with reason
o Story archived with complete history
• If REFUSED (Missing Docs):
o System sends back to Content Manager
o Email sent to writer with missing items list
o System sets follow-up reminder for deadline
o When docs received, returns to Legal Review
• If MODIFICATIONS NEEDED:
o System routes back to Negotiation stage
o Content Manager re-negotiates specific terms
o Once modified, returns to Legal Review
FR-3.7.5: Legal Review Timeline Tracking
• System must track:
o Days in legal review
o Average time per legal reviewer
o Checklist completion percentage
o Document upload dates
o Follow-up actions taken
• System must alert if:
o Review pending > 7 days
o Missing documents deadline passed
o Critical compliance items not addressed
FR-3.7.6: Legal Review Access & Notifications
• Only Legal team can edit review form
• Finance team can view (preparing for payments)
• All stakeholders can view status and checklist progress
• Notifications:
o Legal team notified when review assigned
o Reminders if pending > 5 days
o Writer notified if documents missing
o All parties notified of final decision
FR-3.7.7: Legal Compliance Reporting
• System must maintain compliance dashboard showing:
o % of contracts with complete documentation
o Common missing documents
o Average legal review time
o Rejection reasons (aggregated)
o Risk assessment distribution

3.7.3 Success Criteria
• Legal review completed in < 5 business days
• 100% of critical documents verified before approval
• Clear audit trail for compliance purposes
• Zero contracts signed without legal approval
• Missing document follow-up automated

## **6. NON-FUNCTIONAL REQUIREMENTS**
### **6.1 Performance Requirements**
**Response Times:**
- Page load: < 2 seconds (first load)
- Page load: < 1 second (subsequent loads, cached)
- Form submission: < 1 second
- Search results: < 500ms
- Dashboard refresh: < 2 seconds
- File upload: Progress visible within 200ms
- File download: Starts within 500ms
**Throughput:**
- Support 100 concurrent users
- Handle 1,000 API requests/minute
- Process 50 file uploads simultaneously
**Database:**
- Query response: < 200ms (95th percentile)
- Support 100,000 records in main tables
- Support 1,000,000 records in audit logs
### **6.2 Scalability Requirements**
**Vertical Scaling:**
- System must scale from 50 to 500 users without code changes
- Database must scale from 10GB to 500GB
**Horizontal Scaling:**

- Stateless application (can add more servers)
- Database read replicas for reporting
- File storage scales automatically (S3/Supabase)
**Future Growth:**
- Architecture supports microservices migration if needed
- API-first design allows multiple frontends
### **6.3 Reliability & Availability**
**Uptime:**
- Target: 99.5% uptime (3.6 hours downtime/month acceptable)
- Scheduled maintenance: Weekends only, announced 48 hours in advance
**Data Integrity:**
- Zero data loss tolerance for submitted stories, contracts, payments
- Automatic backups every 24 hours
- Point-in-time recovery within 7 days
- Database transactions ensure ACID properties
**Error Handling:**
- Graceful degradation (if one service fails, others continue)
- User-friendly error messages (never show stack traces)
- Automatic retry for transient errors
- Error logging for debugging
### **6.4 Security Requirements**
**Authentication:**
- Secure login (hashed passwords, bcrypt or better)
- Session timeout after 30 minutes inactivity
- Maximum 5 failed login attempts, then temporary lockout
- Password requirements:
- Minimum 8 characters
- At least 1 uppercase, 1 lowercase, 1 number, 1 special character
- Optional: Multi-factor authentication (MFA)

- Optional: Single Sign-On (SSO) integration
**Authorization:**
- Role-based access control (RBAC)
- Row-level security (users see only their data)
- Action-level permissions (who can approve, reject, etc.)
- Audit trail of all permission changes
**Data Protection:**
- HTTPS only (TLS 1.2+)
- Sensitive data encrypted at rest (NIC, NTN, bank details)
- Passwords never stored in plain text
- API keys/secrets stored securely (environment variables, not code)
- Regular security updates
**File Security:**
- Virus scanning on upload
- File type validation
- File size limits enforced
- Access control (presigned URLs for downloads)
- No direct file system access
**API Security:**
- API authentication (JWT tokens)
- Rate limiting (prevent abuse)
- Input validation (prevent SQL injection, XSS)
- CORS configured correctly
- No sensitive data in URLs or logs
### **6.5 Compliance Requirements**
**Data Privacy:**
- GDPR compliance (if handling EU data)
- Pakistani data protection laws
- User consent for data processing
- Right to data deletion (if required by law)

- Privacy policy and terms of service
**Financial Compliance:**
- Withholding tax calculations accurate
- Tax records maintained for 7 years
- Payment records auditable
- Anti-money laundering (AML) checks for high-value contracts
**Audit Trail:**
- All actions logged (who, what, when)
- Logs immutable (cannot be edited or deleted)
- Logs retained for 5 years
- Logs exportable for audits
### **6.6 Usability Requirements**
**Ease of Use:**
- New users can submit story in < 10 minutes (no training)
- Evaluators can complete evaluation in < 15 minutes
- Interface intuitive (95% task completion without help)
- Help documentation available for all features
**User Training:**
- User guide (PDF) provided
- Video tutorials for key workflows (5-10 minutes each)
- In-app tooltips for complex features
- FAQ section
**Error Recovery:**
- Auto-save drafts every 2 minutes
- Undo functionality where applicable
- Clear error messages with suggested actions
- Support contact clearly visible
### **6.7 Maintainability Requirements**

**Code Quality:**
- Code commented and documented
- Consistent coding standards
- Modular architecture (easy to update one part)
- Automated tests (unit, integration)
- Code review process
**Deployment:**
- CI/CD pipeline for automated deployment
- Zero-downtime deployments
- Easy rollback if issues occur
- Staging environment for testing
**Monitoring:**
- Error tracking (Sentry or similar)
- Performance monitoring (response times, errors)
- Usage analytics (page views, active users)
- Alerting for critical issues
**Documentation:**
- System architecture documented
- API documentation (if exposing APIs)
- Database schema documented
- Deployment process documented
- Runbook for common issues

**Browsers:**
- Chrome 90+ (primary)
- Firefox 88+

- Edge 90+
- No Internet Explorer support
**Devices:**

- Desktop (Windows, Mac, Linux)

**Backup Schedule:**
- Database: Daily full backup at 2 AM
- Files: Continuous backup (S3 versioning)
- Backup retention: 30 days
**Recovery Objectives:**

## **8. APPENDICES**
### **8.1 Assumptions**
1. Users have modern web browsers and stable internet
2. Organization has email server or can use third-party service
3. Content creators are familiar with basic form filling
4. File uploads are primarily PDFs and Office documents
5. Organization has budget for cloud hosting
6. 50-100 users initially, may grow to 500+ in 2 years
7. System will be primarily used during business hours (9 AM - 6 PM)
8. Users are proficient in English (primary language)
9. Organization has IT support for user issues
10. Payment processing happens outside this system (system tracks, doesn't process payments)
### **8.2 Dependencies**

1. Hosting platform (Vercel, Railway, or similar)
2. Database service (Supabase or self-hosted PostgreSQL)
3. File storage (Supabase Storage, S3, or Cloudflare R2)
4. Email service (SMTP, Resend, or SendGrid)
5. Domain name and SSL certificate
6. Third-party UI library (shadcn/ui, Material-UI, or Ant Design)
7. Modern development tools (Node.js, TypeScript, etc.)

**Time:**
- Must be delivered in 15 days (working prototype)

- Must use technologies team is familiar with
- No steep learning curve
